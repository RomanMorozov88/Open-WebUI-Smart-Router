# Open WebUI Smart Router 🤖🎛️

Интеллектуальный маршрутизатор запросов (асинхронный скрипт-фильтр) для **Open WebUI**, который автоматически переключает локальные нейросети-эксперты на сервере **LM Studio** в зависимости от контекста вашего запроса и динамически управляет видеопамятью (VRAM).

В отличие от правил-эвристик, решение о маршрутизации принимает **отдельная маленькая модель-роутер** (класс ~3B, постоянно дежурит в VRAM). Она анализирует запрос и отдаёт ключ нужного эксперта за доли секунды — это даёт гораздо более гибкое и точное распределение, чем фиксированные словари ключевых слов.

> **💡 О железе и моделях:** Экосистема и все перечисленные ниже модели **подбирались для 16 GB VRAM и 64 GB RAM**. Это не догма — для своей конфигурации вы можете свободно заменить как модель-роутер, так и любых экспертов (см. разделы про настройку роутера и конфиг экспертов).

## 📋 Системные требования и Необходимое ПО

Для развертывания полноценной локальной ИИ-станции вам понадобятся:

1. **[LM Studio (v0.4.0+)](https://lmstudio.ai)** — Локальный бэкенд-сервер инференса моделей. Обязательна версия 0.4.0+ с поддержкой встроенного REST API управления моделями.
2. **[Open WebUI](https://github.com/open-webui/open-webui)** — Профессиональный фронтенд-интерфейс чата.
3. **[Docker Desktop](https://docker.com)** — *(опционально)* — Для развертывания Open WebUI и поискового движка через контейнеры. Если Docker не нужен, Open WebUI можно запустить как **нативный десктоп-приложение** без контейнеров.
4. **[SearXNG](https://github.com/searxng/searxng)** — *(опционально)* — Приватный метапоисковый движок для предоставления локальным моделям актуального доступа в Интернет (RAG). Нужен только если вы хотите включить локальным моделям веб-поиск.
5. **[Hugging Face](https://huggingface.co)** — Библиотека ИИ-моделей для скачивания GGUF-файлов (рекомендуемые авторы квантов: `bartowski` и `lmstudio-community`).

> **💡 Опциональные компоненты:** пункты 3–4 необязательны. Минимальный рабочий стек — это LM Studio и Open WebUI. WebUI можно запускать как нативный десктоп-приложение (без Docker), а SearXNG подключать только при необходимости веб-поиска (RAG).

## ✨ Ключевые фичи проекта

* **Ультра-быстрый асинхронный инференс:** Скрипт переведен на полностью асинхронную архитектуру (`async/await` и `aiohttp`), что исключает любые микрофризы интерфейса Open WebUI при обработке запросов.
* **Модель-роутер вместо эвристик:** Выбор эксперта выполняет маленькая быстрая модель (класс ~3B), которая получает системный промт со списком экспертов и их описаниями и возвращает ключ нужного эксперта одним словом. Подробнее — в разделе «Контекст модели-роутера».
* **Автоматический VISION при изображениях:** Если в сообщении есть изображение (`data:image`, `<img>` или `image_url`), запрос принудительно направляется на VISION-эксперта **без обращения к роутеру**.
* **Мгновенная очистка VRAM (Smart Unload):** При смене эксперта и включённом флаге `enable_unload_model` роутер не ждет таймаута TTL, а отправляет принудительный асинхронный API-запрос на выгрузку предыдущей модели. Поддерживается по умолчанию.
* **Умное удержание контекста (Context Lock):** Скрипт игнорирует короткие реплики (короче **15 символов**) и сообщения, начинающиеся с триггерных слов (`что`, `почему`, `why`, `fix`, `исправь`, `поясни`, `explain`, `да`, `нет`, `yes`, `no`, `но`, …), принудительно оставляя вас в контексте текущей модели.
* **Ручное переключение (!-команды):** Вы можете принудительно сменить контекст чата на любого эксперта в любой момент. Работают как **имена экспертов** (`!CODER`, `!CREATIVE`), так и **кастомные команды-алиасы** (`!код`, `!фото`, `!творчество`, `!новая`…). Команды абсолютно **нечувствительны к регистру**.
* **Два режима !-команд:**
  * `!команда` (без текста) — мгновенное переключение контекста: Open WebUI выводит статус «Expert set: X» через эмиттер, а внутренний технический запрос к модели сводится к минимальной заглушке (см. раздел «Контекст модели-роутера»).
  * `!команда <текст>` — команда срезается из сообщения, а остаток текста отправляется выбранному эксперту (удобно: `!код Напиши функцию сортировки…`).
* **Нативный статус-бар сессии (`!status`):** Команда перехватывается асинхронным эмиттером (работает в любом регистре). Open WebUI мгновенно выводит Markdown-панель с текущим экспертом, сервером и моделью-роутером; сам запрос при этом сводится к минимальной технической заглушке на модели-роутере, без пустых пользовательских ответов. Компаньоны — `!commands` (список экспертов) и `!commands/<EXPERT>` (кастомные команды конкретного эксперта).
* **Устойчивый конфиг экспертов:** `experts_config` в Valves можно править вручную через UI — фильтр сам отбрасывает невалидные записи и неверные типы, защищает зарезервированные команды `!status` и `!commands`, схлопывает дубликаты команд, а при битом JSON откатывается на конфиг по умолчанию.
* **Механизм заглушек (`null`):** Модели можно временно отключить в Valves. Скрипт автоматически выполнит мягкий фолбэк на базовую модель (`GENERAL`).

## ⚙️ Настройка серверной части (LM Studio)

Менеджер памяти LM Studio должен быть переведен в многомодельный JIT-режим:

1. Откройте LM Studio ➡️ вкладка **Local Server** (иконка сети слева).
2. В правой панели **Server Settings** найдите блок управления памятью JIT (Just-in-Time).
3. Выставьте следующие тумблеры:
   * **`Just-in-Time Model Loading`** ➡️ **ВКЛЮЧИТЬ (Зеленый)**
   * **`Auto unload unused JIT loaded models`** ➡️ **ВКЛЮЧИТЬ (Зеленый)**
   * **`Max idle TTL`** ➡️ Выставьте **`5`** или **`10`** минут.
   * **`Only Keep Last JIT Loaded Model`** ➡️ **ОБЯЗАТЕЛЬНО ВЫКЛЮЧИТЬ (Серый)** *(Критично! Если включен — сервер будет падать в ошибку HTTP 500)*.
4. **🧠 Оптимизация размера контекста (Context Window):** 
   Для рабочих моделей — **`CODER`** (`qwen2.5-coder-14b-instruct`), **`GENERAL`** (`gemma-4-12b-it`) и **`VISION`** (`qwen3-vl-8b-instruct`) — в настройках их профилей внутри LM Studio обязательно поднимите размер контекста **с дефолтных `8192` до `32768` (32K)**. Архитектура моделей и связка железа (16GB VRAM + DDR5) позволяют комфортно удерживать такой объем памяти без просадки по скорости. Для VISION это особенно важно: без поднятого контекста картинка (особенно в полном разрешении и вместе со всей историей, которую пересылает Open WebUI) превышает окно и сервер отвечает ошибкой переполнения контекста.
5. Загрузите модель-роутер (например `Qwen2.5-3B`) и зафиксируйте параметры её генерации: `Temperature = 0.0`, **`Max Tokens = 20`**.
   * **Почему `Max Tokens = 20`:** роутер должен вернуть **только один ключ эксперта** — одно слово в верхнем регистре (например `CODER`). 20 токенов с большим запасом покрывает такой ответ, при этом обрезание `max_tokens` на коротком ответе не сработает даже на «болтливых» моделях. Качество маршрутизации при этом не страдает, а скорость генерации остаётся максимальной. Ставить можно и другое значение — это не запрещается, просто 20 является разумным компромиссом между скоростью и надёжностью.
6. **⚠️ Внимание по Системным промптам:** Оставьте поле *System Prompt* в настройках моделей на стороне LM Studio абсолютно пустым! Весь контекст и системный промт роутера доставляет сам скрипт-фильтр через Open WebUI — дублирование промтов на стороне сервера нарушит работу маршрутизации.
7. Нажмите синюю кнопку **Start Server** (порт по умолчанию: `1234`).

## 🔌 Интеграция в Open WebUI

1. Откройте Open WebUI под учетной записью администратора.
2. Перейдите в **Admin Panel** ➡️ **Settings** ➡️ **Functions**.
3. Нажмите кнопку **+ Create a function** в правом верхнем углу, выберите тип **`Filter`** и задайте имя (например, `Smart Router`).
4. Вставьте полный Python-код скрипта `filter.py` из данного репозитория и нажмите **Save**.
5. В общем списке функций активируйте тумблер напротив `Smart Router`, зайдите в его настройки и включите флаг **`Globally` (Глобально)**. Роутер активирован для всех чатов!
6. В настройках функции доступны параметры **Valves**:
   * `api_url` — адрес сервера LM Studio (по умолчанию `http://localhost:1234/v1`);
   * `api_key` — ключ (заглушка `lm-studio`, для локального сервера подходит);
   * `router_model` — имя маленькой модели-роутера (по умолчанию `llama-3.2-3b-instruct`; замените на вашу, например `qwen2.5-3b-instruct`);
   * `enable_unload_model` — включать ли **принудительную выгрузку** предыдущего эксперта при смене (по умолчанию `False`). Нужен только для классического режима LM Studio (без JIT), где памятью управляют вручную. В JIT-режиме (рекомендуемая настройка из этого README) сервер сам выгружает простаивающие модели по TTL, поэтому ручная выгрузка излишня и даже вредна — она может выгружать модель, которая вскоре снова понадобится, вызывая лишние перезагрузки. Подробнее — см. [«Технические детали и нюансы»](#-технические-детали-и-нюансы);
   * `experts_config` — JSON-конфиг экспертов. Чтобы **отключить** эксперта, задайте его `model_id` как `null` (запросы пойдут на `GENERAL`). Здесь же можно задать свои модели и кастомные команды.
7. **Установите модель-роутер как модель по умолчанию:** На клиенте чата (слева внизу, селектор моделей) выберите вашу модель-роутер и нажмите **Set as selected model** (в интерфейсе иначе: «установить как модель по умолчанию»). Это гарантирует, что каждый новый чат будет начинаться именно на ней, а фильтр уже сам переключит на нужного эксперта по первому сообщению.

## ⚙️ Контекст модели-роутера

Сердце маршрутизации — **отдельная маленькая модель-роутер** (класс ~3B, постоянно дежурит в VRAM). Она получает список доступных экспертов, их описания и текст запроса, а возвращает **ровно один ключ эксперта в верхнем регистре**. Ниже — как это устроено.

### Роль роутера

Роутер **не является экспертом** и не отвечает пользователю — он только выбирает, кому из экспертов передать запрос. Именно поэтому для него берут маленькую и быструю модель: решение принимается за доли секунды, а «жирные» тяжелые модели загружаются только по необходимости.

> **Важно про размер роутера:** модели класса `Qwen2.5-0.5B` в качестве роутера **не рекомендуются**. Из-за малого количества слоев внимания они путают полярные абстрактные категории (например, принимают команду *«Напиши функцию...»* за творческий `CREATIVE` вместо `CODER` из-за триггера *«Напиши»*). Модели класса **3B** полностью лишены этой проблемы.

### Системный промт роутера

Фильтр собирает для роутера следующий системный промт (отправляется в каждом запросе):

```text
You are an intelligent request router.
Your task is to analyze the user's request and determine which expert to transfer it to.
Choose exactly one key from the allowed list: [CODER, GENERAL, VISION, MATH_LOGIC, CREATIVE, RESEARCH, TRANSLATOR].
Answer STRICTLY WITH ONE WORD (the chosen key in uppercase). No punctuation, no explanations.
GENERAL is the DEFAULT: choose it for greetings, general questions, or anything not clearly matching a specialized expert.
Use a specialized expert only when the request clearly matches its role. When unsure, choose GENERAL.
TRANSLATOR is ONLY for explicit translation or rewrite requests, NOT for questions written in a foreign language.
```

В поле пользовательского запроса подаётся список экспертов с их `description` и сам текст запроса. Из ответа роутера берётся ключ (заголовок регистра — не важно), и запрос направляется соответствующему эксперту.

### Правила принятия решений

* **GENERAL — дефолт по умолчанию.** Выбирается для приветствий, общих вопросов, единиц измерения, подсчётов и всего, что не попадает чётко под специализированного эксперта. Когда роутер сомневается — он обязан выбрать `GENERAL`, а не «угадывать» специализацию.
* **Специализированный эксперт — только при явном совпадении.** `CODER`, `VISION`, `CREATIVE`, `TRANSLATOR` задействуются лишь когда запрос однозначно соответствует их роли.
* **`TRANSLATOR` — только явный перевод/переписывание.** Вопрос, *заданный* на иностранном языке, — это НЕ запрос на перевод и должен уходить на `GENERAL` (или профильный эксперт), а не на `TRANSLATOR`.
* **`CONTEXT` / follow-up** — обрабатывается **на стороне фильтра, без запроса к роутеру**: короткие реплики (< 15 символов) и триггерные слова (см. «Context Lock» выше) оставляют вас в текущей модели.

### Почему `description` так важен

Роутер выбирает эксперта именно по полю `description` (подставляемому в промт). Поэтому формулировки экспертов специально «сужающие»: например, `TRANSLATOR` явно говорит *«NOT for questions asked in a foreign language»*, а `GENERAL` — *«DEFAULT for anything not clearly covered»*. Такая формулировка заметно уменьшает ложные срабатывания роутера и перекладывает «сомнительные» запросы на безопасный `GENERAL`.

## ✅ Как роутер принимает решение

Маршрутизация — это не «роутер решает всё из коробки». Часть запросов вообще не доходит до роутера: фильтр обрабатывает спец-команды, картинки и короткие follow-up **на своей стороне**. Ниже — полная таблица решений.

### Поток сообщения до момента обращения к роутеру

| # | Что получил inlet | Куда идёт запрос | Роутер вызывается? |
|---|---|---|---|
| 1 | Спец-команда `!status` / `!commands` / `!commands/<EXPERT>` | Заглушка на роутер + Markdown-панель в UI | Нет (прямая заглушка) |
| 2 | Контекст-команда без текста (`!code`, `!код`) | Заглушка на роутер + панель «Expert set», **трекер = целевой эксперт** | Нет (прямая заглушка) |
| 3 | Контекст-команда с текстом (`!code <текст>`) | Остаток `<текст>` к целевому эксперту, **трекер = целевой эксперт** | Нет |
| 4 | Сообщение с картинкой | На `VISION`-эксперта, **трекер = VISION** | Нет |
| 5 | Короткое/триггерное сообщение **и** есть трекер активного эксперта | Остаётся на текущем эксперте (Context Lock) | **Нет** |
| 6 | Короткое/триггерное, но трекера нет (новый чат) | `_route_first_message` → **роутер решает** | ✅ Да |
| 7 | Длинный/обычный вопрос, трекер = активный эксперт | `_determine_next_model` → **роутер решает** | ✅ Да |
| 8 | Длинный/обычный вопрос, трекера нет | `_route_first_message` → **роутер решает** | ✅ Да |

> **Короткое** — сообщение короче 15 символов или начинающееся с триггерного слова (`что`, `почему`, `why`, `fix`, `исправь`, `поясни`, `explain`, `да`, `нет`, `yes`, `no`, `но`, …). **Трекер** — модульное состояние фильтра, запоминающее последнего активного эксперта по чату (см. «Технические детали»).

### Решение роутера (для случаев 6-8)

Когда роутер всё же вызывается, его решение интерпретируется так:

| Роутер вернул | Условие | Итог |
|---|---|---|
| Тот же эксперт, что в трекере | `expert == last_assistant_model` | **Остаёмся** на текущем эксперте |
| Другой эксперт | `expert != last`, не служебный | **Переключаем** (и выгружаем старый, если `enable_unload_model`) |
| Неизвестный ключ / служебный (например `CONTEXT`) | fallback | Остаёмся на трекере |

### Автоматика против ручных команд

* **Длинные/обычные запросы** — роутер **всегда** решает автоматически: вернуть запрос тому же эксперту или переключить. Это не требует команд.
* **Короткие follow-up** — теперь **автоматически** остаются на активном эксперте через трекер (Context Lock), не дёргая роутер.
* **Ручные `!`-команды** нужны только когда вы **сознательно** хотите переключить целевую модель принудительно (роутер на обычный вопрос мог бы выбрать `GENERAL`).

  `INFO: [Smart Router] Unloading 1 instance(s) matching 'qwen2.5-coder-14b-instruct'`
  `INFO: [Smart Router] Successfully unloaded model: qwen2.5-coder-14b-instruct`

  `INFO: [Smart Router] Context continuation. Staying on: qwen2.5-coder-14b-instruct`

  Отправка команды `!status` мгновенно выводит Markdown-панель Open WebUI прямо над полем ввода с текущим экспертом, сервером и моделью-роутером, а сам запрос сводится к минимальной технической заглушке на модели-роутере. Команды `!commands` и `!commands/<EXPERT>` показывают списки доступных экспертов и их кастомных команд.

## 🔧 Технические детали и нюансы

Служебные особенности реализации, которые стоит знать, если вы заглядываете «под капот» фильтра или что-то ведёт себя неожиданно.

### VISION и переполнение контекста (важно для картинок)

При загрузке изображения обязательно поднимите окно контекста `qwen3-vl-8b-instruct` в LM Studio до **`32768`/32K** (как уже рекомендовано для `CODER`/`GENERAL`). Нативный размер фотографии кодируется Qwen3-VL патчами и занимает несколько тысяч токенов; при дефолтных `8192` картинка легко превышает окно и сервер отвечает `request (...) exceeds the available context size (8192)`. Усугубляется это **особенностью Open WebUI**: она пересылает на каждый запрос **всю историю чата целиком, включая все ранее загруженные картинки в полном разрешении** (полный base64 в поле `content`), поэтому размер запроса растёт заметно быстрее, чем видно при одиночной проверке той же картинки в интерфейсе LM Studio.

### Инструменты и хук `request` (очистка тулов для служебных команд)

Команды `!status`, `!commands`, `!commands/<EXPERT>` и `!`-переключатели без текста отправляют роутеру единственное служебное сообщение-заглушку (`SYSTEM_REPLY_MARKER`). В хуке `inlet` удалять `body["tools"]` бесполезно — Open WebUI пересобирает список инструментов из `tool_ids`/builtin-тулов/MCP уже после выполнения `inlet`. Поэтому очистка выполняется в хуке **`request`** (срабатывает в самом конце `process_chat_payload`, после инжекции тулов), но только когда единственное сообщение — это заглушка (проверка `_is_routing_placeholder`). Так роутер (`llama-3.2-3b-instruct` с поддержкой лишь одиночного tool-call) не получает вызовы инструментов и не падает с «This model only supports single tool-calls at once!». Для обычных запросов к экспертам инструменты сохраняются (могут быть нужны, например, RESEARCH/web-search).

### Состояние фильтра — в памяти процесса

Трекер «активного эксперта» (используемый для Context Lock и `!status`), а также любые переменные уровня модуля живут **в памяти процесса**:
* сбрасываются при **перезапуске Open WebUI** и при **пересохранении фильтра**;
* у каждого **воркера** (`uvicorn`) своя копия состояния;
* ведётся **по чатам** через `__chat_id__` (fallback — общий ключ `__global__`);
* в `self`-класс данные **не хранятся** — объект-модуль кэшируется Open WebUI, а вот `self` создаётся заново на каждый запрос, поэтому кросс-запросное состояние держится на уровне модуля (`_LAST_EXPERT_MODEL_BY_CHAT`).

Для локальной одно-воркерной установки этого достаточно. Если запускаете несколько воркеров — учитывайте, что контекстная привязка сработает не во всех запросах.

### JIT и `enable_unload_model`

Фильтр умеет **принудительно выгружать** предыдущего эксперта при смене (параметр Valves `enable_unload_model`, по умолчанию `False`). Это нужно только для **классического режима** LM Studio (без JIT), где памятью управляют вручную. В **JIT-режиме** (рекомендуемая настройка из этого README) сервер сам выгружает простаивающие модели по TTL, поэтому ручная выгрузка излишня и даже вредна — она может выгружать модель, которая вскоре снова понадобится, вызывая лишние перезагрузки. Включайте `enable_unload_model` осознанно, проверив поведение на своей связке.

### SearXNG и порт 8080 (важно для web-поиска)

По умолчанию **и Open WebUI, и официальный Docker-образ SearXNG слушают порт `8080`** (compose-шаблон SearXNG пробрасывает `0.0.0.0:8080->8080/tcp`). Если занять этот же порт под SearXNG — открыв `http://localhost:8080` в браузере, вы вместо чата Open WebUI получите страницу поиска SearXNG. Это частая проблема, характерная для запуска с `--network=host` или проброса `-p 8080:8080`.

**Решение:** пробросьте SearXNG на другой порт хоста, отличный от `8080`, например `-p 8888:8080` (это официальный пример из документации SearXNG), и укажите этот адрес (например `http://localhost:8888`) в настройках web-поиска Open WebUI. Порт `8080` оставьте только за Open WebUI, чтобы чат открывался по привычному адресу.

## 📌 Примечания и ограничения

* **Нет ретраев сетевых запросов.** Фильтр рассчитан на локальный стабильный сервер LM Studio: если роутер недоступен или вернул ошибку, запрос упадёт с ошибкой (независимо от локальной задачи — это осознанное решение, чтобы не маскировать проблемы с сервером и не усложнять логику).
* **`!status` и `!commands` зарезервированы.** Их нельзя переопределить кастомными командами экспертов — фильтр принудительно отбрасывает такие попытки из `experts_config`.
* **`enable_unload_model` по умолчанию выключен** — подробнее о JIT и принудительной выгрузке см. [«Технические детали и нюансы»](#-технические-детали-и-нюансы).
* **Инструменты не доходят до роутера при служебных командах** (пример хука `request`) — почему чистка тулов делается в `request`, а не в `inlet`, см. в [«Технических деталях и нюансах»](#-технические-детали-и-нюансы).
